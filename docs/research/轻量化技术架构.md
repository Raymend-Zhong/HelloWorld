# 儿童习惯打卡平台轻量化技术架构调研

## 一、调研说明

- 调研问题：针对当前业务需求，选择兼顾本地部署、在线发布、离线打卡、跨设备同步和低维护成本的技术架构。
- 决策用途：作为后续架构决策记录和实施规格的输入。
- 调研日期：2026-09-11。
- 资料范围：仅使用官方文档、标准维护方文档和官方源码仓库。
- 业务依据：`CONTEXT.md`、`docs/prd/prd.md`、`docs/prd/clarifications.md`。
- 本文不修改业务需求；部署方式、离线范围和同步方案仍需在 ADR 中正式确认。

本文用以下标记区分结论性质：

- **【事实】**：来源直接陈述或可由官方资料直接验证。
- **【推断】**：由事实结合本项目规模和使用方式推导。
- **【建议】**：面向本项目的架构取舍。

## 二、需求对架构的约束

### 2.1 已确认的关键场景

- 系统服务一个家庭，第一版固定一个家长账户、两个孩子账套。
- 家长维护任务池和目标，孩子在孩子端提交或撤销未清算打卡，家长审核并执行每日清算。
- 同一孩子可有多个并行目标；同一次打卡可供多个目标分别计分。
- 清算支持撤销、修改、重新清算，并保留仅家长可见的修订历史。
- 手机、平板、电脑均可能使用，页面需适配触控和鼠标。
- 网页断网时仍需支持打卡，联网后自动同步；相反操作以操作时间较晚者为准。
- 网页可能在一台本地电脑上运行，也可能发布到互联网。
- 第一版追求轻量、易操作和易维护，不需要社交、支付、通知、多家庭租户或大规模并发。

### 2.2 由业务推导出的技术要求

- **【推断】** 清算、撤销清算、连续奖励和目标状态恢复包含多表一致性，适合由一个权威服务在数据库事务中完成，不能只依靠界面临时计算。
- **【推断】** 清算修订历史要求保存事实记录和规则快照，单纯覆盖当前积分会使历史无法重放和审计。
- **【推断】** 浏览器离线数据只能作为待同步副本。若要跨设备共享同一家庭数据，必须有一个可被各设备访问的权威数据源。
- **【推断】** 家庭级写入量很低，主要负载是短事务和小型查询，没有引入分布式数据库、缓存集群或消息系统的容量理由。

## 三、浏览器离线能力与硬约束

### 3.1 Service Worker 与本地打开方式

- **【事实】** Service Worker 位于网页、浏览器和网络之间，可以拦截请求、缓存资源并提供离线体验；它只能在安全上下文中使用。HTTPS 是常规条件，浏览器也把 `http://localhost` 视为安全上下文。[MDN：Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)
- **【事实】** 现代浏览器通常把 `file:///` 文件视为不透明来源，同目录文件也不一定同源，可能触发跨域错误。[MDN：同源策略中的文件来源](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy#file_origins)
- **【事实】** SvelteKit 在存在 `src/service-worker.js` 或 `src/service-worker/index.js` 时会打包并自动注册 Service Worker，并提供构建文件、静态资源和应用版本清单。[SvelteKit：Service workers](https://svelte.dev/docs/kit/service-workers)

- **【推断】** “双击 HTML 文件直接打开”无法可靠承载本项目的 PWA、离线缓存和同源数据能力。
- **【建议】** 将“本地使用”定义为启动本地服务后访问 `http://localhost:<端口>`，而不是 `file:///`。这仍是网页形态，且与在线版本复用同一构建产物。
- **【限制】** 手机通过 `http://192.168.x.x:<端口>` 访问家庭电脑时，该局域网 IP 通常不属于安全上下文，Service Worker 不能按线上模式工作。局域网多设备若要求完整离线能力，需要可信 HTTPS；Caddy 可为本地域名或 IP 签发本地证书，但每台客户端必须信任其本地根证书。[Caddy：Automatic HTTPS](https://caddyserver.com/docs/automatic-https)

### 3.2 IndexedDB 与缓存边界

- **【事实】** IndexedDB 是浏览器端事务型数据库，可以保存大量结构化对象并建立索引；数据按来源隔离。[MDN：IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)
- **【事实】** Cache API 适合持久保存 HTTP 请求与响应；IndexedDB 适合结构化数据。浏览器存储默认属于尽力而为模式，设备存储紧张或长期未使用时可能被清除；网页可调用 `navigator.storage.persist()` 请求持久存储，但浏览器可以拒绝。[MDN：存储配额与清理规则](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)、[MDN：StorageManager.persist()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)
- **【事实】** Background Sync API 在部分主流浏览器中仍不可用，不属于 Baseline 能力。[MDN：Background Synchronization API](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API)

- **【建议】** Service Worker 的 Cache Storage 只缓存应用壳、字体、图片、动画和音效；业务数据、当天任务快照和待同步操作存入 IndexedDB。
- **【建议】** 使用 Dexie 4.x 作为 IndexedDB 的薄封装，以减少原生 IndexedDB 的样板代码和升级事务错误。调研时官方发布页显示 Dexie 4.4.6；具体补丁版本在实施时由锁文件固定。[Dexie 官方发布页](https://github.com/dexie/Dexie.js/releases)、[Dexie 官方文档](https://dexie.org/docs/Dexie.js)
- **【建议】** 不把 Background Sync 作为唯一同步触发器。同步应在页面启动、网络恢复、页面回到前台、用户操作完成后和页面保持打开时的短间隔重试中执行；支持 Background Sync 的浏览器可把它作为额外优化。
- **【限制】** 浏览器缓存不能代替备份。用户清理站点数据、使用隐私浏览或浏览器主动清理时，本地待同步记录可能丢失。因此孩子端应明显显示“待同步/已同步”，家长清算前服务端应确认当天操作已接收。

## 四、候选方案比较

| 方案 | 本地使用 | 在线与跨设备 | 离线打卡 | 运维复杂度 | 对本项目的判断 |
| --- | --- | --- | --- | --- | --- |
| 纯静态网页 + IndexedDB | 很轻，但应通过本地 HTTP 服务访问 | 无服务端时无法自动跨设备共享 | 强 | 最低 | 仅适合单设备原型或完全离线版 |
| 单体 Node.js 服务 + SQLite + IndexedDB 队列 | 同一服务可在本地运行 | 单实例在线服务可统一同步 | 强，需要实现小型同步协议 | 低 | **推荐** |
| Firebase/Firestore 托管后端 | 前端可本地开发，正式数据依赖托管服务 | 自动跨设备同步 | 强 | 托管时低 | 在线优先的备选，不满足独立本地运行目标 |
| 自托管 Supabase | 可本地或在线 | 能力完整 | 需另配前端离线策略 | 高于需求规模 | 功能过重，不推荐第一版 |
| PocketBase | 单可执行文件，较轻 | REST、认证和实时能力齐全 | 没有直接替本项目解决离线写入合并 | 较低 | 可做备选后端，但当前稳定性与自研同步成本不优于推荐方案 |

### 4.1 纯静态网页与浏览器本地存储

- **【事实】** IndexedDB 能保存本项目所需的结构化数据和事务；浏览器数据仍受来源隔离、配额和清理策略约束。[MDN：IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)、[MDN：存储配额与清理规则](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- **【推断】** 单台设备、无跨设备共享时，纯静态 PWA 可以完成目标、任务、积分和清算。导入导出 JSON 可以提供人工备份。
- **【推断】** 一旦手机、平板和电脑同时使用，纯静态方案需要自行增加文件传递或远端同步服务；届时它不再是纯静态架构。
- **【推断】** 家长密码若只在前端校验，只能避免误操作，不能形成互联网环境下的安全边界，因为客户端代码和本地数据均由访问者控制。
- **【建议】** 保留为“单设备演示模式”备选，不作为正式数据架构。

### 4.2 轻量单体服务与嵌入式数据库

- **【事实】** SQLite 强调经济、效率、可靠、独立和简单，适合应用程序本地存储；它不需要独立数据库服务器。[SQLite：适用场景](https://www.sqlite.org/whentouse.html)
- **【事实】** SQLite 事务具备原子性、一致性、隔离性和持久性；事务在程序、操作系统或断电中断时仍保证全部完成或完全不发生。[SQLite：事务特性](https://sqlite.org/transactional.html)
- **【事实】** WAL 模式允许读写并发，但所有访问数据库文件的进程必须位于同一主机，不能把 WAL 数据库放在网络文件系统上供多台主机共同写入。[SQLite：WAL](https://www.sqlite.org/wal.html)
- **【事实】** 截至调研日，SQLite 官方最新稳定版为 3.53.4，发布于 2026-07-24。[SQLite：发布历史](https://sqlite.org/changes.html)

- **【推断】** 本项目的数据量和并发远低于 SQLite 的典型边界；一个应用进程、一个数据库文件足以承载。
- **【建议】** 服务端 SQLite 是唯一权威数据源；浏览器 IndexedDB 是离线缓存和待同步队列。所有积分、清算、撤销清算和目标状态迁移均由服务端在事务中执行。
- **【建议】** 在线部署只运行一个写入实例，并把数据库放在本机持久磁盘，不放在 NFS、SMB 或多个容器共享的网络卷中。需要水平扩容时再迁移 PostgreSQL；第一版不为这种假设预付复杂度。

### 4.3 托管后端或同步框架

#### Firebase/Cloud Firestore

- **【事实】** Cloud Firestore 官方客户端可以缓存数据，在恢复网络后同步本地更改；同一文档的多次更改采用最后写入者获胜。Web 端持久离线缓存默认关闭，需要显式启用，官方列出的支持浏览器为 Chrome、Safari 和 Firefox。[Firebase：离线数据](https://firebase.google.com/docs/firestore/manage-data/enable-offline)
- **【推断】** 它能减少离线同步代码，但数据模型、鉴权和运维将与 Firebase 托管服务绑定；要实现不依赖公网服务的本地正式运行，需要另做后端或维护两套模式。
- **【建议】** 如果以后明确选择“仅在线托管、优先免运维”，Firestore 是有效备选；当前不选。

#### Supabase

- **【事实】** 自托管 Supabase 的完整 Docker 方案最低要求 2 核、4 GB 内存和 40 GB SSD，推荐 4 核、8 GB 以上；完整架构包含网关、认证、PostgREST、Realtime、Storage、元数据服务、Studio、Postgres 等多个服务。[Supabase：Docker 自托管](https://supabase.com/docs/guides/self-hosting/docker)
- **【事实】** 自托管者需负责服务器、安全加固、升级、Postgres 维护、备份、灾难恢复和监控。[Supabase：Self-Hosting](https://supabase.com/docs/guides/self-hosting)
- **【推断】** 这些能力远超一个家庭应用的需要，资源和维护成本与“尽量轻量”冲突。
- **【建议】** 第一版不采用；未来若演变为多家庭 SaaS，再重新评估 PostgreSQL/Supabase。

#### PocketBase

- **【事实】** PocketBase 0.40.3 是包含 SQLite、认证、实时订阅、管理界面和 REST 风格 API 的单可执行后端；官方同时声明 1.0 前不保证完整向后兼容，不建议用于无法接受手工迁移的关键生产系统。[PocketBase：官方文档](https://pocketbase.io/docs/)
- **【推断】** PocketBase 很轻，但仍需为本项目实现 IndexedDB 待同步队列、幂等操作、清算事务和定制冲突规则；其通用管理后台对固定家庭场景的收益有限。
- **【建议】** 若团队更熟悉 Go 或希望直接获得管理后台，可作为第二后端候选；当前优先使用单一 TypeScript 技术栈。

## 五、推荐架构

### 5.1 总体结构

```text
手机 / 平板 / 电脑浏览器
├── Svelte 响应式界面
├── Service Worker：应用壳与媒体缓存
└── IndexedDB（Dexie）：当天数据、待同步操作、同步游标
             │
             │ HTTPS；localhost 可使用 HTTP
             ▼
SvelteKit 单体 Node.js 服务
├── 页面与静态资源
├── JSON API / 会话鉴权
├── 同步与幂等处理
├── 目标、连续奖励、清算领域服务
└── SQLite 单文件数据库
             │
             ├── 定时在线备份
             └── 本机外备份副本（在线部署时）
```

- **【建议】** 使用模块化单体：部署上只有一个应用服务和一个 SQLite 文件，代码内部按身份与会话、孩子账套、任务、目标、打卡同步、清算、虚拟养成、备份分模块。
- **【建议】** 页面、API 和领域逻辑放在同一个 SvelteKit 工程中，共享 TypeScript 类型和校验规则；无需单独拆前端仓库与后端仓库。
- **【建议】** 使用同源 API，避免额外 CORS 配置；线上由反向代理终止 TLS，本地由 Node 直接提供 `localhost` 服务。

| 层次 | 建议技术 | 调研日版本基线 | 选择原因与限制 |
| --- | --- | --- | --- |

| 服务端数据库 | SQLite | 3.53.4 或由驱动捆绑的同级修复版 | 无独立数据库服务，事务适合清算和修订历史。[SQLite 发布历史](https://sqlite.org/changes.html) |
| Node SQLite 驱动 | `better-sqlite3` 13.x | 13.0.3，内部 SQLite 3.53.4 | v13 要求 Node 22 以上，提供预编译平台包、事务和备份 API；具体版本由锁文件固定。[源码包配置](https://raw.githubusercontent.com/WiseLibs/better-sqlite3/v13.0.3/package.json)、[官方发布页](https://github.com/WiseLibs/better-sqlite3/releases) |
| 浏览器数据库 | IndexedDB + Dexie | Dexie 4.4.6 | 原生标准能力加薄封装，不使用其云同步服务。[Dexie 发布页](https://github.com/dexie/Dexie.js/releases) |
| 离线资源 | 原生 Service Worker + Cache API | 浏览器标准 | SvelteKit 已提供构建清单和自动注册，无需额外 PWA 框架。[SvelteKit：Service workers](https://svelte.dev/docs/kit/service-workers) |
| TLS/反向代理 | Caddy 2.x，可选 | 部署时固定稳定补丁版 | 线上自动申请和续订证书，并反向代理到 Node；本地单机 `localhost` 不需要它。[Caddy：Automatic HTTPS](https://caddyserver.com/docs/automatic-https)、[Caddy：reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) |

版本执行规则：

- **【建议】** `package-lock.json` 提交仓库，生产使用 `npm ci`；不使用 `latest` 漂移安装。
- **【建议】** 主版本升级必须先阅读官方迁移说明、备份 SQLite，并运行清算回放与离线同步测试。
- **【建议】** Node 只跟随 LTS 主版本；框架和数据库驱动采用稳定发行版，不采用 `next`、`beta` 或 `rc`。
- **【限制】** Node 自带 `node:sqlite` 在 Node 26.8.2 文档中仍标为“Release candidate”，因此第一版优先选择成熟的 `better-sqlite3` 接口，后续可在内置模块稳定后减少一个依赖。[Node.js：node:sqlite](https://nodejs.org/api/sqlite.html)

### 5.3 中间件取舍

第一版需要：

- SQLite：权威业务数据库。
- Dexie：浏览器离线存储封装。
- Caddy：只在公开上线且运行平台未提供 HTTPS 时使用。
- SvelteKit 服务端钩子：会话解析、家长权限检查、请求日志和错误统一转换。

第一版不需要：

- Redis：没有跨实例缓存、分布式锁或高吞吐会话需求。
- 消息队列：清算由家长同步触发，动画在客户端播放，没有长耗时异步任务。
- 独立任务调度器：核心业务无定时自动清算；备份可由进程内定时器或操作系统定时任务完成。
- 对象存储：内置头像、主题、动画和音效随应用发布；第一版不允许用户上传自定义媒体。
- Elasticsearch 或全文检索：数据规模和查询需求不成立。
- 独立 API 网关：单应用、同源访问，Caddy 已覆盖 TLS 和反向代理。
- ORM：领域规则复杂度集中在行为和历史快照，而非跨数据库兼容；直接使用参数化 SQL、迁移文件和小型仓储层更透明。若实施团队明确偏好 ORM，可在不改变架构的前提下另行评估。

## 六、数据与事务设计

### 6.1 权威数据模型

**【建议】** 至少包含以下概念表，实际字段在规格阶段确定：

| 数据组 | 主要记录 | 设计目的 |
| --- | --- | --- |
| 身份与设备 | 家长凭证、服务端会话、已授权设备 | 保护家长功能和公网孩子入口 |
| 孩子账套 | 两个孩子、昵称、头像、主题、老师形象 | 固定两个账套但允许修改展示资料 |
| 模板与任务池 | 年龄任务模板、孩子任务、停用状态、默认规则 | 保留模板复制与任务停用语义 |
| 目标 | 目标、奖励、计划时长、状态、目标积分、历史最高积分、虚拟养成模板 | 每目标独立积分与成长进度 |
| 目标任务配置 | 任务引用、积分与扣分快照、计划、连续奖励设置、配置生效时间 | 历史不随任务池和后续配置修改而变化 |
| 打卡事实 | 任务发生项、完成/撤销操作、设备、业务日期、客户端操作时间、接收时间 | 支持共享打卡、离线同步、幂等和最后写入者规则 |
| 清算 | 清算批次、目标明细、奖扣项、规则快照、修订版本、撤销关系 | 支持重算和仅家长可见的修订历史 |
| 数据版本 | 模式迁移版本、同步变更序号 | 数据库升级和增量同步 |

### 6.2 清算一致性

- **【建议】** 一次目标清算在单个 SQLite 事务中完成：冻结当日任务结果与配置快照、计算奖扣和连续次数、更新目标当前积分与历史最高积分、写入清算明细、必要时变更目标状态。
- **【建议】** 一个孩子的多个目标可以在同一事务中清算；若任何目标计算失败，则整次清算回滚，避免界面显示一半成功。
- **【建议】** 积分使用整数，不使用浮点数。
- **【建议】** 撤销清算不删除旧记录，而是新增修订版本并标记旧版本被替代；重新计算受影响日期之后的连续状态和目标状态。
- **【事实】** SQLite 的单事务更新满足原子提交，适合上述全成或全败行为。[SQLite：事务特性](https://sqlite.org/transactional.html)

### 6.3 时间与任务周期

- **【建议】** 保存 `家庭时区`，第一版默认为 IANA 时区 `Asia/Shanghai`。
- **【建议】** 业务日期和周周期按家庭时区计算；网络传输时间戳使用带时区的 ISO 8601 字符串或 UTC 毫秒值。
- **【建议】** 打卡事实同时保存业务日期、客户端操作时间和服务端接收时间，不能仅靠服务器收到请求的日期推断任务属于哪一天。

## 七、离线同步设计

### 7.1 第一版离线范围

- **【建议】** 离线支持：打开已缓存应用、查看最近同步的孩子资料/进行中目标/当天任务、孩子提交打卡、孩子撤销未清算打卡、查看待同步状态。
- **【建议】** 需要联网：家长登录验证、任务池和目标管理、豁免、补录、每日清算、撤销及重新清算、历史导出和恢复。
- **【推断】** 把高一致性家长操作限制为联网，可以显著缩小冲突面，同时完整满足“断网时打卡”的核心价值。

### 7.2 操作队列与幂等

- **【建议】** 每次完成或撤销形成不可变操作，字段至少包含：`operationId`、`deviceId`、`childId`、`taskOccurrenceKey`、`action`、`clientOccurredAt`、`createdOffline`。
- **【建议】** IndexedDB 在同一事务中更新本地展示状态并写入 outbox，避免“界面显示已打卡但没有待同步操作”。
- **【建议】** 服务端以 `operationId` 唯一约束实现幂等；同一批操作重复上传只返回原结果，不重复计分。
- **【建议】** 服务端接收操作后分配单调递增 `changeSequence`；客户端保存同步游标，按游标拉取遗漏变更和最新快照。
- **【建议】** 操作同步成功不等于积分已生效。界面区分“已打卡/待同步/已同步”和“已清算”；积分仅在家长清算后改变。

### 7.3 最后写入者规则

- **【建议】** 对同一 `taskOccurrenceKey` 的完成与撤销，比较 `(clientOccurredAt, serverReceivedAt, operationId)`：客户端操作时间较晚者优先；时间相同用服务端接收时间，再以操作 ID 稳定决胜。
- **【建议】** 所有原始操作均保留，当前状态由胜出操作投影得到，便于排查和重新清算。
- **【限制】** 离线设备时钟可能不准，导致“实际较晚”的操作拥有较早时间。第一版既然不提供人工冲突处理，只能接受该限制；同步时应检测明显超前或滞后的设备时钟并提示家长校准，而不静默改写原时间。
- **【建议】** 已清算日期收到新的离线操作时，不自动改积分；标记该日期“清算后收到变更”，由家长撤销并重新清算，防止后台静默改变孩子已看到的结果。

## 八、鉴权与权限

### 8.1 家长端

- **【建议】** 单一家长账户使用密码登录；服务端只保存带随机盐的 `scrypt` 派生值，不保存明文密码。Node.js 24 自带异步 `crypto.scrypt()`。[Node.js：crypto.scrypt](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)
- **【建议】** 登录后签发随机、不透明的服务端会话 ID，放入 `HttpOnly`、`SameSite=Lax`、线上 `Secure` 的 Cookie；会话记录保存在 SQLite，可撤销并设置空闲与绝对过期时间。
- **【事实】** `HttpOnly` 禁止页面 JavaScript 读取 Cookie，可降低会话值被脚本窃取的风险；`Secure` Cookie 在普通 HTTP 站点不能设置，但 localhost 有例外处理。[MDN：Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)
- **【建议】** 所有修改任务、目标、配置、清算、修订和备份的接口都在服务端校验家长会话，不能只隐藏按钮。

### 8.2 孩子端

- **【建议】** 孩子仍然不输入密码；在本地同机模式下选择头像即可进入孩子端。
- **【建议】** 若发布到公网，不能开放匿名写接口。家长登录后为家庭设备进行一次性授权，服务端向该设备发放可撤销的孩子端设备令牌；孩子之后只需选择头像，不感知密码。
- **【建议】** 孩子令牌只允许读取孩子端所需数据，以及提交/撤销尚未清算的打卡；不能访问家长配置、清算修订历史或备份接口。
- **【推断】** 该方式保留“孩子免密码”的业务体验，同时避免任何知道网址的人都能篡改打卡数据。
- **【限制】** 业务已明确不强制阻止两个孩子切换账套，因此设备令牌可覆盖家庭的两个孩子端账套；界面依靠昵称、头像和主题清楚标识当前孩子。

## 九、部署拓扑

### 9.1 本地单机模式

```text
同一台电脑浏览器
    └── http://localhost:3000
            └── Node.js 单体进程
                    └── ./data/family.db
```

- **【建议】** 提供启动脚本或桌面快捷方式，内部执行数据库迁移后启动 `node build`，浏览器访问 localhost。
- **【事实】** `adapter-node` 产物可由 `node build` 启动，并可通过 `HOST`、`PORT` 和 `ORIGIN` 配置地址。[SvelteKit：adapter-node](https://svelte.dev/docs/kit/adapter-node)
- **【建议】** 默认只监听 `127.0.0.1`，防止无意暴露到局域网；若明确需要局域网设备访问，再配置可信 HTTPS 和防火墙。
- **【限制】** 本地电脑关机时其他设备无法同步；只在 localhost 使用时也没有跨设备能力。需要手机和平板稳定共享时，应使用在线单实例模式或常开家庭服务器。

### 9.2 在线单实例模式

```text
互联网浏览器
    └── HTTPS / Caddy 或托管平台 TLS
            └── Node.js 单体实例
                    ├── 持久磁盘/family.db
                    └── 持久磁盘/backups/
```

- **【建议】** 部署在一台 Linux 主机或支持持久磁盘的单容器平台；应用只能有一个写入实例。
- **【建议】** 数据库和备份目录挂载持久磁盘；代码镜像可以替换，数据卷不能随发布销毁。
- **【建议】** 若平台已提供 HTTPS 和反向代理，不再叠加 Caddy；自管 VPS 才使用 Caddy。
- **【事实】** Caddy 可自动申请、续订公开域名证书并将 HTTP 重定向到 HTTPS。[Caddy：Automatic HTTPS](https://caddyserver.com/docs/automatic-https)
- **【限制】** 不选择没有持久文件系统的纯函数计算平台，因为 SQLite 文件必须稳定存在于同一主机。

### 9.3 同一构建的配置差异

仅通过环境变量区分，不分叉业务代码：

- `ORIGIN`：本地为 `http://localhost:3000`，线上为公开 HTTPS 地址。
- `HOST`、`PORT`：控制监听地址。
- `DATABASE_PATH`：SQLite 文件的绝对路径。
- `BACKUP_PATH`：备份目录。
- `SESSION_SECRET`：线上必须由部署环境注入，不提交仓库。
- `TRUSTED_PROXY`：只有位于已知反向代理之后才启用转发头解析；SvelteKit 官方提示代理头若配置不当可被伪造。[SvelteKit：adapter-node](https://svelte.dev/docs/kit/adapter-node)

## 十、SQLite 并发、持久性和备份

### 10.1 运行配置

- **【建议】** 开启外键约束、WAL 和合理的 busy timeout；启动时读取并验证实际 PRAGMA 值，避免拼写错误被 SQLite 静默忽略。[SQLite：PRAGMA](https://sqlite.org/pragma.html)
- **【建议】** 使用单个应用进程持有写连接，所有积分和清算写入均为短事务。
- **【事实】** WAL 允许读写并行，但 WAL 文件属于数据库持久状态；直接复制数据库时遗漏 `-wal` 文件可能丢失已提交事务或损坏副本。[SQLite：WAL 文件](https://www.sqlite.org/wal.html#the_wal_file)
- **【建议】** 不在应用运行时使用普通文件复制命令直接复制主数据库。

### 10.2 备份策略

- **【事实】** SQLite Online Backup API 可以在数据库仍被使用时渐进复制到另一个数据库文件，只在短暂读取阶段锁定源库。[SQLite：Online Backup API](https://www.sqlite.org/backup.html)
- **【事实】** `better-sqlite3` 提供 `.backup(destination)`，备份结果是普通 SQLite 文件，备份过程中数据库仍可正常使用。[better-sqlite3：API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)
- **【建议】** 每晚清算完成后或每天固定时间执行在线备份；默认保留 7 个每日、4 个每周和 12 个每月备份。
- **【建议】** 在线部署至少把一份备份复制到主机之外；本地模式在家长端提供“一键导出备份”，并定期提醒保存到另一个磁盘或个人云盘。
- **【建议】** 若在线数据的重要性提高且可以接受一个额外进程，可选 Litestream 将 SQLite 变更持续复制到对象存储；它无需修改应用代码，但第一版不强制引入。[Litestream 官方说明](https://litestream.io/)

### 10.3 恢复流程

1. 停止写入并关闭应用进程。
2. 保留当前数据库作为故障现场副本。
3. 将选定备份恢复到新文件。
4. 执行 `PRAGMA integrity_check` 和应用模式版本检查。
5. 在临时实例验证孩子、目标、最近打卡和最近清算。
6. 原子替换正式数据库并启动应用。
7. 验证登录、读取和一条可撤销的测试操作。

- **【事实】** SQLite 提供 `PRAGMA integrity_check` 检查数据库页、索引和约束一致性。[SQLite：PRAGMA integrity_check](https://sqlite.org/pragma.html#pragma_integrity_check)
- **【建议】** 每季度至少演练一次恢复。没有验证过的备份不能视为可恢复备份。

## 十一、明确不采用的方案与原因

### 11.1 不采用“只有 localStorage”

- `localStorage` 只保存字符串，适合少量简单状态；本项目需要索引、事务、操作队列和结构化快照，IndexedDB 更匹配。[MDN：存储技术比较](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria#what_technologies_store_data_in_the_browser)

### 11.2 不采用“浏览器 SQLite/WASM 作为唯一数据库”

- 浏览器侧数据库仍受来源存储配额和清理策略影响，且不能自行解决多设备权威同步。
- 本项目数据规模不需要在 IndexedDB 上再叠加 SQLite WASM；这会增加文件系统适配、Worker 和迁移复杂度。

### 11.3 不采用 PostgreSQL 作为第一版默认数据库

- PostgreSQL 能提供更高并发和多实例能力，但本项目固定家庭、低写入量，没有独立数据库服务的收益。
- 若未来变为多家庭 SaaS、需要多实例水平扩展或多人同时高频写入，再通过仓储边界和迁移脚本切换。

### 11.4 不采用微服务、Redis 和消息队列

- 领域事务高度相关，拆服务会引入分布式一致性和额外部署单元。
- 当前没有后台长任务、高吞吐事件或跨实例协调需要。

### 11.5 不直接使用托管同步服务

- Firebase 能减少同步实现，但会使本地独立运行失去同构后端。
- Supabase 自托管资源和职责明显超过项目规模。
- PocketBase 仍需定制本项目的离线操作语义和清算事务，且 1.0 前兼容承诺有限。

## 十二、风险与限制

| 风险或限制 | 影响 | 缓解方式 |
| --- | --- | --- |
| 浏览器清理 IndexedDB | 未同步打卡可能丢失 | 请求持久存储、显示同步状态、尽快前台同步、清算前核对 |
| Background Sync 支持不完整 | 关闭页面后不保证后台上传 | 页面启动、`online`、回前台和操作后主动同步 |
| 设备时钟偏差 | 最后写入者判断可能不符合真实顺序 | 保存接收时间、检测大幅偏差、提示校时、保留原操作 |
| 清算后收到迟到操作 | 已展示积分与新事实冲突 | 不静默重算，提示家长撤销并重新清算 |
| SQLite 单写入实例 | 不能直接水平扩容 | 家庭场景保持单实例；规模变化时迁移 PostgreSQL |
| 数据库位于网络文件系统 | WAL 锁失效或数据库风险 | 数据库只放实例本地持久磁盘 |
| 本地服务电脑关机 | 其他设备不能访问或同步 | 使用在线部署或常开家庭服务器 |
| 局域网 HTTP 非安全上下文 | Service Worker/PWA 能力不可用 | 单机用 localhost；局域网部署配置受信任 HTTPS |
| 孩子免密码 | 公网匿名写入风险 | 家长一次性授权设备，发放最小权限设备令牌 |
| 新框架或驱动升级 | PWA、原生模块或数据迁移回归 | 锁版本、先备份、运行迁移和离线回归测试 |

## 十三、建议结论

**【建议】** 第一版采用 SvelteKit 模块化单体、Node.js 24 LTS、服务端 SQLite、浏览器 IndexedDB/Dexie 和原生 Service Worker。SQLite 是权威数据库，IndexedDB 保存只读快照和待同步操作。公开部署时单实例运行并使用持久磁盘；本地部署时由同一 Node 构建在 localhost 启动。

这一方案需要数据库。原因不是数据量大，而是清算、撤销清算、规则快照、目标状态恢复和跨设备同步都需要可靠事务与权威状态。SQLite 无独立服务，仍符合轻量化原则。

第一版同步只覆盖孩子端当天打卡和撤销；家长配置、清算和历史修订保持联网操作。服务端通过操作 ID 去重，以客户端操作时间为主要顺序、接收时间和操作 ID 为稳定决胜，保留全部原始操作。这样能满足已确认的“最后操作生效”，同时控制实现复杂度。

默认不引入 Redis、消息队列、PostgreSQL、对象存储、托管 BaaS 或通用同步框架。它们都有合理使用场景，但当前没有带来足以抵消维护成本的价值。

## 十四、备选路径

### 备选 A：单设备纯本地 PWA

适用条件：明确只在一台设备使用，不需要自动跨设备同步，能够接受手工导出备份。

技术：SvelteKit 静态构建、Service Worker、IndexedDB/Dexie，无服务端数据库。家长密码只作为本机误操作防护。

迁移路径：保留与推荐方案相同的领域模型和操作 ID；需要跨设备时增加单体服务，把 IndexedDB 数据导入 SQLite。

### 备选 B：Firestore 在线优先

适用条件：明确放弃完全独立的本地正式运行，接受托管平台依赖，并优先减少同步代码和服务器运维。

技术：静态 PWA、Firestore Web SDK、Firebase Authentication/安全规则。需要重新设计家庭设备授权、清算原子边界和成本上限。

### 备选 C：PocketBase 后端

适用条件：希望使用单可执行后端和自带管理界面，且愿意跟随 1.0 前的迁移变化。

技术：Svelte 前端、PocketBase、IndexedDB 离线 outbox。清算和同步仍需自定义服务端扩展或可信 API 层。

## 十五、实施前验证清单

这些验证应先以技术探针完成，再写 ADR 和完整规格：

1. 用目标浏览器矩阵验证首次在线加载后，断网能否打开应用并查看当天任务。
2. 在 Chrome、Safari、Firefox 的桌面和移动端验证 IndexedDB 写入、持久存储请求及重新打开后的保留情况。
3. 验证完成、撤销、重复上传、乱序上传和断网恢复时的幂等与最后写入者规则。
4. 人为调快或调慢设备时间，验证偏差提示和确定性决胜逻辑。
5. 验证同一任务被两个目标引用时，一次打卡分别按各目标快照计分。
6. 验证清算事务失败时没有部分目标成功。
7. 验证撤销较早日期的清算后，后续连续奖励、目标积分和已达成状态能正确重算。
8. 验证清算后才同步到达的离线操作不会静默修改积分，而会触发家长修订提示。
9. 在目标部署平台验证 SQLite 文件和备份目录经过重启、升级和重新部署后仍保留。
10. 在运行中执行在线备份，再从备份恢复到临时实例并运行 `PRAGMA integrity_check`。
11. 验证家长接口拒绝孩子设备令牌，孩子令牌只能提交或撤销未清算打卡。
12. 验证线上 Cookie 的 `HttpOnly`、`Secure`、`SameSite` 属性和会话失效流程。
13. 测量应用壳及动画音效资源体积，确保首次加载后可完整缓存，并在配额不足时给出中文错误提示。
14. 验证 localhost 模式；若需要局域网手机访问，再单独验证证书分发和各设备安全上下文。

## 十六、待 ADR 决策项

建议下一阶段只关闭以下会影响实现的架构决策：

1. 正式选择推荐的单体 Node.js + SQLite 架构，还是采用备选方案。
2. 第一版是否同时交付本地启动包和在线部署配置，还是先交付其中一种但保持架构兼容。
3. 确认离线范围为“当天查看、打卡、撤销”，家长管理和清算必须联网。
4. 确认公网孩子端采用家长一次性设备授权，不要求孩子输入密码。
5. 确认 SQLite 单实例约束和默认备份保留策略。
